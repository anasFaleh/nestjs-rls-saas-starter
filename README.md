# NestJS RLS SaaS Starter

**A NestJS backend for multi-tenant B2B SaaS where tenant isolation is enforced by PostgreSQL, not by remembering a `WHERE tenant_id = ?`.**

Most multi-tenant starters filter by `tenant_id` in application code. One forgotten filter, one raw query, one new
developer, and customer A sees customer B's data. This starter puts the rule in the database with
**Row Level Security**, connects the app as a role that **cannot** bypass it, and ships **tests that prove it**.

```ts
// No tenant filter anywhere. PostgreSQL returns only the current tenant's rows.
list() {
  return this.prisma.withCurrentTenant((tx) => tx.project.findMany());
}
```

**Website:** https://anasfaleh.github.io/nestjs-rls-saas-starter/ · **Pro edition** (users, RBAC, billing, jobs, deploy) is coming: [join the waitlist](https://anasfaleh.github.io/nestjs-rls-saas-starter/#waitlist).

## What you get

- **Postgres RLS done right**: `ENABLE` + `FORCE` row level security, policies with both `USING` and `WITH CHECK`,
  tenant set per transaction with `set_config(..., true)` so pooled connections never leak a tenant.
- **A runtime role that cannot cheat**: the API connects as `app_user` (not superuser, no `BYPASSRLS`, owns no table) and
  **refuses to boot** if it is ever pointed at a role that could bypass RLS.
- **Secure tenant resolution**: API key → tenant through a narrow `SECURITY DEFINER` function. The client never chooses
  its tenant; a `X-Tenant-Id` header or a `tenantId` in the body does nothing.
- **Secure by default**: every route needs a key unless marked `@Public()`. Strict request validation with zod.
- **Tests that fail if isolation breaks** (real PostgreSQL, Vitest): cross-tenant read / update / delete / insert,
  raw SQL, concurrency, leaked settings, plus a **privilege audit** that fails when someone adds a table without deciding
  its grants and RLS. Turn RLS off on one table and 15 tests go red.
- **Prisma 7** with the `pg` driver adapter, TypeScript strict, ESM (`nodenext`), NestJS 12.
- **Tenant admin CLI**: create tenants, issue / revoke API keys (only a SHA-256 is stored), suspend / activate.
- **Production basics**: validated env, `/healthz` + `/readyz`, multi-stage Dockerfile (non-root), GitHub Actions CI
  with a schema-drift check.
- **AI-agent friendly**: `AGENTS.md` teaches Claude Code / Cursor / Copilot the tenant rules, so generated code stays safe.

## Quick start

Requirements: Node 22.12+, Docker (or any PostgreSQL 14+).

```bash
cp .env.example .env              # then change the app_user password
npm install
docker compose up -d              # PostgreSQL 16 on localhost:5434
npx prisma generate
npm run db:setup                  # creates the DB roles, then applies migrations
npm run build
npm run tenants -- create --name "Acme"   # prints a tenant id and an API key (shown once)
npm run start:dev
```

```bash
KEY=sk_...   # from the command above
curl -X POST localhost:3000/projects -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{"name":"First"}'
curl localhost:3000/projects -H "Authorization: Bearer $KEY"
```

Create a second tenant and try to read the first tenant's project with its key: `404`.

## Managed PostgreSQL (Neon, Supabase, RDS...)

Works when the migration user is **not** a superuser (tested: an owner role with only `CREATEROLE`). The setup script
creates the roles, grants itself membership in `tenant_resolver`, and verifies the roles are safe before migrating.
Run `npm run db:setup` with `DATABASE_URL` pointing at that owner user.

## Run the tests

```bash
npm test            # unit tests, no database
npm run test:e2e    # against the database in .env (creates and deletes its own tenants)
npm run typecheck && npm run lint
```

## Project layout

```
prisma/
  schema.prisma                        models (tenants, api_keys, projects)
  migrations/..._init                  tables (generated by Prisma)
  migrations/..._tenant_security       grants, RLS policies, resolve_api_key() (hand-written)
scripts/db/setup-roles.mjs             creates app_user + tenant_resolver (run before migrations)
src/
  config/          validated env (zod)
  prisma/          PrismaService: withTenant(), withCurrentTenant(), safe-role check at boot
  tenancy/         TenantContext (AsyncLocalStorage), interceptor, tenant admin functions
  auth/            API keys, global ApiKeyGuard, @Public()
  projects/        example tenant-owned resource: copy this for your own
  health/          /healthz, /readyz
  cli/tenants.ts   tenant admin CLI
test/              e2e: tenant isolation, DB privilege audit, HTTP API
docs/              architecture, adding a tenant table
site/              landing page (GitHub Pages)
```
